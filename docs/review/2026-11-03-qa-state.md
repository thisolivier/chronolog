## 4. Bugs found (ranked)

Classification key: **REAL BUG** (feature broken), **REGRESSION** (worked at sprint sign-off, broken now),
**NOT IMPLEMENTED**, **DRIVER ISSUE** (not a product bug; listed in the driver README instead).

### 1. Timesheet crashes and never renders when two entries in a day share a colour-bar key — REAL BUG (sprint 017)
- **What:** `WeekStrip.svelte:136` keys the per-day colour bar with
  `{#each colorSegments as segment (segment.colorClass + segment.percentage)}`, and
  `computeColorSegments` (`:87-93`) emits **one segment per entry**. Two entries on the same day with the
  same client colour and the same percentage produce a duplicate key; Svelte 5 throws
  `each_key_duplicate` and the whole `TimeEntriesPanel` stays on "Loading weeks…" for every week
  (40-timesheet-crash-each-key-duplicate, 99-fail-T2-after-reload-and-delete).
- **Why it matters:** every client currently has the same colour (bug 6), so **any two entries of equal
  length on one day** (two 1-hour meetings, two 0-minute timer saves) make the time view unusable until a
  row is deleted through the API or database.
- **Repro:** create two entries for today with the same duration (e.g. two `0:30` via Add Entry), reload.
  Console: `Keyed each block has duplicate key \`bg-rose-4000\` at indexes 0 and 1 … in WeekStrip.svelte`.
- **Fix:** key by `entry.id` (or index), and aggregate segments per client rather than per entry.

### 2. Backlinks are never created from the editor — REAL BUG (present since Task 8; sign-offs tested the API only)
- **What:** the `WikiLink` TipTap node (`src/lib/components/notes/extensions/wiki-link.ts`) defines
  `renderText` (`[[id]]`) but no `tiptap-markdown` serializer, so `editor.storage.markdown.getMarkdown()`
  falls back to HTML. The saved `content` of note B is literally
  `Gamma links to <span data-wiki-link="" data-note-id="INTL.20261103.002" …>INTL.20261103.002</span>`.
  The server's `updateNoteLinks()` (`queries/note-links.ts:44`) only parses `[[…]]`, so `note_links` stays
  empty: the table had **zero rows** after the whole run, `GET /api/notes/INTL.20261103.002/backlinks`
  returns `[]`, and "Linked from" never appears (30-note-A-linked-sections).
- **Also affected:** the Markdown export contains the HTML span instead of `[[id]]`; the raw-mode textarea
  shows it too. Sprint 014-QA's "Backlinks PASS" was obtained by `PUT`-ing `[[id]]` markdown directly.
- **Repro:** in note B type `[[`, pick note A, wait for autosave, open note A → no "Linked from".
- **Fix:** add `addStorage() { return { markdown: { serialize(state, node) { state.write('[[…]]') } } } }`
  to the extension (and a parse rule for `[[…]]` on the way in, which the input rule already handles
  for typed text).

### 3. Raw → Rich toggle blanks the editor and throws on every raw keystroke — REAL BUG (sprint 012-CL)
- **What:** `NoteEditor.svelte:319-327` swaps `<textarea>` and the editor `<div bind:this={editorElement}>`
  with `{#if editorMode === 'raw'}`. TipTap was mounted into the original div; when the div is removed the
  editor keeps the detached element, so after toggling back `.tiptap` count is 0 and the pane is empty
  (35-after-toggle-back-to-rich). While in raw mode `editorElement` is `null`, so each `setContent()` in
  `handleRawInput` → `onUpdate` → `resolveAllChronologImages(null)` throws
  `Cannot read properties of null (reading 'querySelectorAll')` (the one page error of the driver run).
- **Data is safe:** the raw edit *is* saved (reload shows "Added in raw mode" as an `h2`).
- **Repro:** open a note → "◇ Rich" toggle → type → toggle again.
- **Fix:** keep the editor div mounted (`class:hidden`) instead of `{#if}`, and declare `editorElement`
  with `$state` (svelte-check already warns `non_reactive_update` at `:55`).

### 4. Timesheet does not refresh after a timer save or an Add Entry modal save — REAL BUG
- **What:** `TimerWidget.handleSave()` and `handleAddEntryCreated()` (`TimerWidget.svelte:175-215`) only
  reset the widget; nothing tells `TimeEntriesPanel` to `refreshWeeks()`. The new entry appears only after
  a reload (27-after-timer-save-no-reload vs 27-after-reload-timer-entry; 34-after-add-entry-modal).
  Inline-row creates and card edits do refresh, which is why this went unnoticed.
- **Repro:** Add Entry → fill → Save; or Start Timer → Stop → Save. Today's section does not change.
- **Fix:** dispatch an event (the app already uses `window.dispatchEvent('note-saved')`) or lift a
  `refresh` callback through the layout.

### 5. Client colour left border never shows on cards or the new-entry row — REAL BUG (sprint 017)
- **What:** `getClientBorderClass()` returns `border-rose-400` (all sides) and `TimeEntryCard.svelte:187` /
  `NewEntryRow.svelte:53` also apply `border border-stone-200`. Both set `border-color`; Tailwind emits
  `border-stone-200` later, so it wins. Computed `border-left-color` = `oklch(0.923 0.003 48.717)`
  (stone-200) on every card and on the new-entry row even after choosing a contract.
- **Fix:** emit `border-l-rose-400`-style classes (and list them for Tailwind's scanner), or set the colour
  via a CSS variable / inline style.

### 6. All clients share colour index 0 — NOT IMPLEMENTED (code review risk #8, confirmed live)
- `clients.color_index` is 0 for every row (Acme Corp included); there is no admin control. Sidebar dots,
  cards and WeekStrip bars are therefore all rose. This is also what makes bug 1 trivially reachable.

### 7. Deliverable / work type cannot be set on manual entries — REGRESSION (CL-6; sprint 017)
- `NewEntryRow` lost `DeliverableSelect` in the 017 rewrite, `AddTimeEntryModal` never had one, cards have
  no inline editor, and `PUT /api/time-entries/:id` drops the fields (code review §1). The only path that
  sets a deliverable is the timer completion form, and it works (card shows "Phase 1").

### 8. Wiki-link in a time-entry card renders but does nothing on click — REAL BUG (code review risk #7, confirmed)
- `WikiLinkRenderer` renders a `button[title^="Go to note"]`; `TimeEntriesPanel.svelte:274` mounts
  `TimeEntryCard` without `onNoteLinkClick`. Probe P11: click → still in time mode
  (36-after-clicking-description-link).

### 9. Timer completion form loses its contract after a reload; sub-minute timers save 0 m — REAL BUG (minor)
- After Stop → reload, the recovered form shows "Select a contract…" with Save disabled although the server
  draft has `contract_id` set (99-fail-P9-timer-save-refresh, 23-timer-completion). The user must re-pick.
- Duration is minute-granular (`queries/time-entries.ts:181-186`): a 4-second timer saved `0m`
  (27-after-reload-timer-entry). Combined with bug 1 two such saves crash the view.
- Pause is cosmetic (code review risk #3) — not re-verified here.

### 10. Move feedback never visible — REAL BUG (cosmetic)
- See C1 above. `moveMessage` renders inside the editor header, which unmounts when the note leaves the list.

### 11. Minor usability findings
- `[[` autocomplete orders by recency and selects the first item on Enter; typing `[[INTL.` + Enter linked
  the wrong note in the driver run (13-description-autocomplete). Showing content preview lines
  (the `wip/2026-05-27-debug-session` branch does this, code review §4) would help.
- Notes have no title: exports are all `untitled-note.md`, lists show the first line.
- The Add Entry modal accepts only `H:MM` durations while the inline row accepts `2h30m`.
- `/login` does not redirect an authenticated user to `/`.
- Reloading in notes mode reopens the app in time mode (selection lost).
- `GET /api/work-types?deliverableId=<non-uuid>` returns 500 (Postgres cast error) instead of 400.

## 6. Verdict — how close to "usable daily"?

For one consultant tracking time and notes, the core loop works today: register/login, admin set-up of
clients and contracts, inline time entry with time/contract/description editing, the week strip and
status chip, timer start/stop/save, note creation with autosave, wiki-link autocomplete and
click-through, Markdown/print export, note move, and all three automated suites green. But it is not
yet safe to use daily because of two things that will bite within the first week: bug 1 crashes the
entire time view the moment two same-length entries land on one day (made almost certain by every client
sharing a colour), and bug 4 hides every timer-saved entry until a reload, which makes the app look like
it lost data. Behind those, the note-linking story is half-real (backlinks are never indexed from the
editor, card links do nothing), the raw-markdown toggle wipes the editor, and the deliverable field —
needed for invoicing — regressed to timer-only. None of these is large: bugs 1, 3, 4 and 5 are
one-file fixes, bug 2 is a small TipTap serializer, and a colour picker in admin would unlock the
whole colour system. A focused one-to-two-day stabilisation sprint covering bugs 1–8, followed by a
re-run of `e2e-playwright/manual-checklist/qa-driver.mjs` (with the README's known-limitation fixes) and
a human pass over the NOT VERIFIABLE rows, would bring the web app to daily-usable; Tauri (D) and mobile
(B) remain untested.
