## Objective

One request creates or updates up to 200 notes, and one request creates up to 500 time entries, with a per-item result, so the secretary imports a month of history with one command per file.

## Tasks

1. **`POST /api/notes/batch`** (new file `src/routes/api/notes/batch/+server.ts`). Body `{ items: [...], atomic?: boolean }`, at most 200 items. Each item is either a create `{ contractId, title?, content?, createdAt? }` (same fields and validation as `POST /api/notes`, including the user-timezone backdating from 034) or an update `{ id, title?, content?, append?: string, expectedUpdatedAt? }` (same semantics as `PATCH /api/notes/[noteId]`; `append` adds a blank line and the text; without `expectedUpdatedAt` an update is applied unconditionally, and the response says so). Response `200 { results: [{ index, ok, id?, updatedAt?, error?, code? }], created, updated, failed }`. With `atomic: true`, run in one transaction and roll back on the first failure, returning that item's error plus `code: "batch_rolled_back"` for the others. Call the existing query functions (`createNoteForUser`, `updateNoteForUser`) rather than duplicating them; if you need a transaction-aware variant, add a thin wrapper in a **new** file `queries/notes-batch.ts`.
2. **`POST /api/time-entries/batch`** (new file). Items have the fields of `POST /api/time-entries` (contractId, date, duration or start/end, description, deliverableId?, workTypeId?, noteId?), at most 500, validated through `assertEntryReferences` (032) per item, same response shape and `atomic` option.
3. **CLI `chronolog import notes <file>` and `chronolog import entries <file>`** (new file `cli/commands/import.mjs`, one registration line in `cli/chronolog.mjs`). Input is JSON Lines or a JSON array. Items use the CLI's human references, not ids: `contract` (`ACME/Website`), `deliverable`, `workType`, `note` (note id), `date` (`YYYY-MM-DD`, `yesterday`, …), `duration` (the usual forms). The CLI resolves references once per distinct value (one `contracts --json` call, one deliverables call per contract touched), rejects the whole file before sending anything if any reference is ambiguous or unknown (exit 3 listing the bad lines), then sends in chunks of 100 (notes) or 200 (entries). `--dry-run` resolves and prints what would be sent. `--atomic` passes the flag through per chunk. Output: one line per item (`ok 12 ACME.20261004.003` / `fail 7 invalid_date …`), then a summary; `--json` prints the raw results. Exit 0 if all ok, 1 if any failed. Record created entries in the undo history as a list so `chronolog undo --last-import` deletes them all (confirm per the 031 rule).
4. **Docs and skill.** CLI readme, `cli/CHANGELOG.md` (1.1.0; bump `package.json` to 1.1.0), `docs/LAPTOP-SETUP.md` reference. Skill: a short "Importing history" paragraph (append to the end of `SKILL.md`, under 15 lines, to minimise merge conflicts with 037): build the file, show the owner the dry run, import, keep the file.
5. **Tests.** Unit: both routes (validation, per-item errors, atomic rollback, limits), the CLI resolver on a fixture file with one bad reference. API e2e: import 30 notes (some backdated, one update by id with append) and 60 entries from fixture files via the CLI, verify counts and that `week` shows them; `undo --last-import` removes the entries. No Playwright needed; the existing suite must stay green.

### What was done

1. **`POST /api/notes/batch`** (`src/routes/api/notes/batch/+server.ts`, item rules in `note-batch-item.ts`). `{ items, atomic? }`, 1 to 200 items (more is 400 `too_many_items`, nothing saved). A create `{ contractId, title?, content?, createdAt? }` follows `POST /api/notes` (UUID → `invalid_contract`, ownership → `contract_forbidden`, `createdAt` calendar/future → `invalid_date`, backdated to noon in the `X-Timezone` zone, the ID carrying that day). An update `{ id, title?, content? | append?, expectedUpdatedAt? }` follows `PATCH` (markdown clears `contentJson`, word count from markdown, `conflict` with the current `updatedAt` when stale, `note_not_found` for unknown or someone else's note); `append` adds a blank line and the text (the CLI's `appendedContent` rule). Without `expectedUpdatedAt` the result carries `unconditional: true`; a non-atomic append then re-reads and retries (3 attempts) if the note changes between read and write, so nothing is lost. Unknown fields are a per-item 400. Created and updated notes refresh the wiki-link index after the commit. Non-atomic items call `createNoteForUser` / `updateNoteForUser` / `getNoteForUser` unchanged; atomic items use the thin transaction-bound variants in the new `queries/notes-batch.ts` (same `getNextNoteId`, same advisory lock key, same encryption).
2. **`POST /api/time-entries/batch`** (`src/routes/api/time-entries/batch/`). Up to 500 items with the fields of `POST /api/time-entries`, reusing `readDurationFields` and `isValidDate` from `entry-input.ts` and `assertEntryReferences` per item (codes `invalid_date`, `invalid_duration`, `invalid_contract`, `contract_forbidden`, `deliverable_mismatch`, `work_type_mismatch`, `note_not_found`). `startTime` + `endTime` alone count as the range. `noteId` appends `[[id]]` and links like the single route. Atomic items use `queries/time-entries-batch.ts` (insert, note check and links inside the transaction; a link to a missing note is skipped rather than failed, as the single route ignores it).
   - Shared engine `src/lib/server/batch/run-batch.ts` (`readBatchBody`, `runBatch`, `BatchItemError`) with a readme. Response `200 { results: [{ index, ok, id?, updatedAt?, error?, code? }], created, updated, failed }`; with `atomic` one transaction, first failure rolls back, that item keeps its error and every other item reports `batch_rolled_back`.
3. **CLI** `chronolog import notes|entries <file> [--dry-run] [--atomic] [--json]` (`cli/commands/import.mjs`, `cli/lib/import-file.mjs`, `import-items.mjs`, `import-history.mjs`). JSON Lines (blank and `//` lines skipped, real line numbers kept) or a JSON array. References resolved once per distinct value (one contracts call, one deliverables call per contract, one work-types call per deliverable, plus one `/api/me` for date words); any unknown/ambiguous reference refuses the whole file before sending (exit 3, each bad line with up to 5 candidates); an invalid line (not JSON, unknown field) is exit 2, also before sending. Notes: `body` gets the `# title` heading as `note new` does, `content` is used as written, `date` backdates; changes by `id`. Chunks of 100 / 200; `--atomic` per chunk. Output `ok <line> <id>  <summary>` / `fail <line> <code> <message>` and a summary; `--json` prints the results with their lines; exit 1 if any failed. Created entry ids go to `last-import.json`; `chronolog undo --last-import` deletes them all after the 031 confirmation (`--yes` without a terminal), counting ones already gone. A date word the CLI cannot read goes to the server as written, which reports `invalid_date` for that item.
