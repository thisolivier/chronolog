# Sprint 037 — CL: Server-side trash for notes; word count on create

**Status:** ready for review (not merged)
**Branch:** `sprint-037-CL/note-trash` · **Worktree:** `.claude/worktrees/sprint-037-CL` · **Port:** 5215
**Sources:** owner request 2026-11-04; sprint 034 sign-off (restored notes get a new ID, links dangle; CLI notes store word count 0); backlog journeys A-10 (wiki-links to deleted notes do nothing).

## Objective

Deleting a note, from the browser or the CLI, moves it to a server-side trash where it keeps its ID, its wiki-links, its backlinks and its time-entry links. Restoring brings everything back exactly. Trash empties itself after 30 days. A note created over the API has a correct word count from the start.

## Design (decided)

- `notes.deleted_at timestamptz null`, with a partial index on `(user_id) where deleted_at is not null`. One Drizzle migration. No rows are ever hard-deleted by the app except by the purge.
- Every read query that lists, searches, titles, previews, autocompletes or resolves a note excludes `deleted_at is not null` unless a caller passes `includeDeleted`. Audit `queries/notes.ts`, `queries/note-links.ts`, the search and titles routes, the backlinks route and the time-entry "linked notes" reads; list each one in the sign-off.
- `note_links` and `note_time_entries` rows are left alone on delete, so restore is a single `update ... set deleted_at = null`. The wiki-link renderer treats a link to a trashed note as a muted "deleted" link that, on click, offers to restore it (a small inline confirm); the backlinks panel hides trashed sources.
- Purge: `deleteNoteForUser` (now a soft delete) also hard-deletes this user's rows with `deleted_at` older than 30 days, in the same transaction, cascading links. No scheduler. `scripts/purge-note-trash.mjs` exists for a manual run and is documented.
- The CLI's local trash files from sprint 034 are dropped: `note delete` calls the API, prints the ID and "restore with `chronolog note restore <id>` within 30 days". `note restore <id>` calls `POST /api/notes/[noteId]/restore`; with no id it lists the server trash (`GET /api/notes/trash`). Remove the trash-file code and its tests; migrate nothing (the files, if any, stay on disk and are mentioned in the readme once).
- `POST /api/notes` computes `word_count` from `contentJson` when present, else from markdown (`calculateWordCountFromMarkdown` already exists from 034).

2. `DELETE /api/notes/[noteId]` soft-deletes and purges; `POST /api/notes/[noteId]/restore` (404 if not trashed or not yours; 409 `id_taken` cannot happen since the row keeps its ID, but a restore onto an archived contract is allowed and reported); `GET /api/notes/trash` lists id, title, contract, deletedAt, purge date. The browser's Delete button uses the same route and the editor panel shows a short "Moved to trash. Undo" toast for ten seconds that calls restore (keep it small; it lives in `NoteEditorPanel.svelte`).

4. Wiki-link rendering for trashed targets (A-10) and the inline restore; backlinks hide trashed sources.
5. Word count on create (API). Backfill existing rows with `word_count = 0` and non-empty content with `scripts/backfill-note-word-counts.mjs`. **It must run inside the production container**: `docker exec chronolog-prod-app node scripts/backfill-note-word-counts.mjs --dry-run` then `--apply`. The image copies only `scripts/migrate.mjs` (Dockerfile line 41) and has no `src/`, so the script is plain `.mjs` with no `.ts` imports: it uses the `postgres` package and Node `crypto` to open the `enc1:` envelope (copy the envelope logic from `scripts/encrypt-existing.mjs` into a shared `scripts/lib/envelope.mjs` and make `encrypt-existing.mjs` import it too), counts words from `content_json` when present else from `content` with the same rules as the app (port the two counters; unit-test that they agree with the TypeScript ones on fixtures), and updates `word_count` only. Add the script and `scripts/lib/` and `scripts/purge-note-trash.mjs` to the Dockerfile's copied files. `--dry-run` prints the count and five sample IDs; `--apply` prints the count updated. Run it on dev and report the count.
6. Tests: unit for every route and the purge window; API e2e: create via CLI (word count > 0), link note B to A, delete A, B's render shows "deleted", restore A, links intact, time-entry link intact; Playwright: delete in the browser, Undo toast restores, and the sidebar/list reflect both.

### What was done

1. **Migration, schema, read paths.** `drizzle/0009_note_trash.sql` (generated): `notes.deleted_at timestamptz null` and `notes_trash_user_id_idx` on `(user_id) where deleted_at is not null`. Applied to the shared dev database (after a `pg_dump` taken from the dev container). Trash, restore, the trash list and the purge live in `queries/note-trash.ts`; `queries/notes.ts` re-exports them and exports `notInTrash`. **Read-path audit** (each excludes trashed rows unless `includeDeleted` is passed; all covered by `src/routes/api/notes/note-trash.test.ts`):
   - `queries/notes.ts`: `listNotesForContract`, `listNotesForUser` (`GET /api/notes`, both the contract and `updatedSince` forms), `getNoteForUser` (`GET /api/notes/[id]`, attachments `GET/DELETE`, `POST /api/time-entries` with `noteId`, `…/time-entries` routes; `includeDeleted` option), `updateNoteForUser` (`PUT`/`PATCH` are 404 on a trashed note).
   - `queries/note-search.ts`: `searchNotesForUser` (`/api/notes/search`, `[[` autocomplete, the note list search) and `getNoteTitlesForUser` (`/api/notes/titles`; `includeDeleted=1` adds `deletedAt`).
   - `queries/note-links.ts`: `getBacklinksForNote` hides trashed sources and is now scoped to the caller (it took no user before; any signed-in user could read another user's backlink titles by note ID). `updateNoteLinks` still treats a trashed target as existing, so links to it are kept and come back on restore.
   - Time-entry "linked notes": `getLinkedTimeEntriesForNote` is reached only through `getNoteForUser` (404 for a trashed note); the week's wiki-links in entry descriptions resolve through `/api/notes/titles` and render as "deleted".
   - `queries/contracts.ts` `listContractsByClientWithNoteCount`: sidebar note counts skip trashed notes.
   - Sprint 038's batch paths (added after the second rebase, at the coordinator's request): `queries/notes-batch.ts` `lockNoteInTransaction` and `updateNoteInTransaction` (an atomic `append`/update to a trashed note is `note_not_found`, the batch's 404, and the whole atomic batch rolls back); `queries/time-entries-batch.ts` `findUserNoteIdInTransaction` (`noteId` on an atomic entry) and `linkTimeEntryToNotesInTransaction` (description links skip trashed notes). The non-atomic batch paths already went through `getNoteForUser` / `updateNoteForUser`. `linkTimeEntryToNote` (notes.ts) now refuses a trashed note too, so the single and non-atomic routes agree: a new link to a note in the trash is not made, while links made before the delete stay and come back with it. `src/lib/server/batch/` itself has no note lookups (only the engine and a test fixture).
   - **Also fixed in 038's code:** `createNoteInTransaction` stored `wordCount: 0`; an atomic batch create now counts the markdown, like `POST /api/notes`.
   - Deliberately unchanged: `getNextNoteId` (sees trashed IDs, so an ID is never reused while its note can come back), `safe-deletion.ts` (a contract delete moves trashed notes too, as the foreign key requires, and counts them), `deleteNoteForUser`'s purge.
2. **Routes and the browser.** `DELETE /api/notes/[id]` soft-deletes and purges the caller's notes trashed more than 30 days ago in the same transaction (FK cascades take their links, time-entry links and attachments); it returns `deletedAt` and `purgeAt` too. `POST /api/notes/[id]/restore` (404 `not_in_trash`; an archived contract is allowed and reported as `contract.archived`). `GET /api/notes/trash` (id, title, contractId, contract, deletedAt, purgeAt). The browser's Delete uses the same route; `NoteEditorPanel.svelte` shows "Moved to trash. Undo" for ten seconds, and Undo restores and reopens the note. `DataService.restoreNote` added (fetch + delegating). New `note-restored` event: the note list reloads and sidebar counts refresh.
   - **Addition:** `GET /api/notes/[id]` answers 404 `note_in_trash` for the caller's trashed note (anyone else gets the plain 404), and the CLI turns it into exit 3 "… is in the trash: `chronolog note restore <id>` brings it back" for `note show/edit/append/delete` (`cli/lib/note-fetch.mjs`).
3. **CLI, skill, docs.** `note delete` calls the API and prints the ID and "Restore with `chronolog note restore <id>` within 30 days"; `note restore <id>` posts to the restore route (exit 3 when not in the trash); `note restore` lists the server trash. `cli/lib/trash.mjs`, its tests and `--contract` on restore are gone; old trash files are left on disk and mentioned once in `cli/readme.md` and the changelog.
